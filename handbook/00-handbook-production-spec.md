# 巨亨ONLINE 官網使用手冊製作規範

- 文件狀態：製作規範初版
- 版本：0.1
- 建立日期：2026-07-31
- 適用對象：產品營運人員、客服人員、後續文件維護與交接人員
- 文件範圍：玩家官網與登入後遊戲大廳的前台功能

## 1. 文件目的

本手冊的主要目的，是讓營運與客服人員能夠快速理解巨亨ONLINE 官網的產品規則、操作流程、玩家可見結果與問題處理方式，並在玩家或代理商提出問題時提供一致、正確且可追溯的說明。

本手冊不是單純的畫面導覽，也不是營運後台操作手冊。每個功能章節都必須同時說明：

- 玩家如何使用功能。
- 系統在不同情況下會出現什麼結果。
- 客服如何判斷問題原因。
- 哪些問題可以直接引導玩家排除。
- 哪些問題必須升級給產品或技術團隊。
- 哪些內容目前尚未定案，不能自行對玩家承諾。

## 2. 適用範圍與排除範圍

### 2.1 納入範圍

- 官網公開頁面與登入入口。
- 年齡確認、註冊、登入、登出與帳號安全。
- 遊戲大廳、遊戲啟動、試玩與正式遊戲流程。
- 錢包、幣別、儲值、金庫、兌換與贈禮。
- 活動、每日任務、排行榜與獎勵卡。
- 站內信、客服工單、聊天、好友、封鎖與檢舉。
- 代理商可能詢問的玩家端功能與規則。
- 客服回覆話術、快速查詢表與問題升級條件。

### 2.2 排除範圍

本手冊不描述以下內容：

- 營運後台的登入、權限、玩家管理、人工加扣款、儲值訂單審核、代理管理與報表操作。
- 遊戲供應商後台與第三方金流後台操作。
- Nuxt、Vue、API、部署、GitHub Actions 等技術維運流程。
- 尚未被產品確認的功能細節。

營運後台將另行製作獨立使用手冊，兩份文件可以互相連結，但不可混寫成同一本。

## 3. 規則優先順序

本手冊以「正式產品目標規則」為最終說明依據，不以目前前端 Mock 行為作為對外說法。

規則來源的優先順序如下：

1. 已確認的產品決策、正式營運規則與對外法遵要求。
2. 已確認的前台產品規格與 API 契約。
3. 已確認的畫面流程與元件文字，用於描述入口、按鈕名稱與畫面位置。
4. 目前前端 Mock 行為，只能作為內部理解現況與找出落差的參考。

若不同來源互相衝突，採用以下處理原則：

- 對玩家與代理商的說法：依正式產品目標規則。
- 對內部人員的現況備註：可以記錄目前 Mock 行為與正式規則的差異。
- 尚未定案的項目：標示為「待產品確認」，不得自行推論或承諾。
- 已知前端 Bug：不得寫成正式產品規則；應記錄預期結果、現況差異與回報方式。

## 4. 文件內容標籤

為了讓交接人員快速辨認內容性質，每章使用以下標籤：

| 標籤 | 用途 |
|---|---|
| **正式規則** | 可作為客服與營運的標準說法，代表產品目標行為。 |
| **操作流程** | 玩家在官網實際執行功能的步驟。 |
| **例外處理** | 輸入錯誤、條件不符、逾時、取消、失敗等分支。 |
| **客服處理** | 客服應確認的資訊與可以提供的處理方向。 |
| **升級條件** | 需要交給產品、技術或其他負責單位的情況。 |
| **目前系統差異** | 目前前端 Mock 與正式規則不一致的地方，只供內部參考。 |
| **待產品確認** | 規則、流程或文案尚未定案，不得作為正式承諾。 |
| **截圖預留** | 初期先保留位置，最終版再補上實際畫面。 |

## 5. 章節架構

預計依下列順序製作，每章獨立交付與確認：

1. 使用手冊導讀與產品總覽。
2. 註冊、登入與帳號安全。
3. 忘記密碼與帳號恢復。
4. 遊戲大廳與遊戲進行方式。
5. 試玩模式與真錢模式。
6. 錢包與遊戲幣別。
7. 儲值與付款。
8. 金庫、幣別兌換與資金轉移。
9. 贈禮功能。
10. 每日任務、活動與排行榜。
11. 獎勵卡與獎勵兌換。
12. 站內信與系統通知。
13. 好友、聊天、封鎖與檢舉。
14. 客服問題回報與案件處理。
15. 代理商常見問題。
16. 客服回覆話術與快速查詢表。
17. 名詞解釋與規則附錄。

章節編號一經採用，後續新增內容以新編號或子章節加入，不任意改動既有編號，避免交接與客服引用失效。

## 6. 每章固定內容格式

每一章至少應包含以下區塊：

1. **本章目的**：說明這一章解決什麼問題。
2. **適用對象**：玩家、營運、客服或代理商。
3. **功能入口**：從哪個頁面或按鈕進入。
4. **使用前提**：是否需要登入、年齡確認、特定幣別、VIP 等級或其他條件。
5. **正式產品規則**：限制、計算方式、狀態定義與不可違反的規則。
6. **標準操作流程**：按照玩家實際操作順序完整描述。
7. **狀態與畫面結果**：成功、處理中、失敗、取消、逾時、拒絕等結果。
8. **情境與例外矩陣**：列出常見問題、原因、玩家看到的結果與建議處理。
9. **客服檢查清單**：客服需要詢問或確認的資料。
10. **客服可直接處理事項**：不需要後台操作即可提供的協助。
11. **升級條件**：何時需要轉產品、技術、金流或其他單位。
12. **禁止事項**：客服不得做出的承諾、不得索取的敏感資訊或不得採用的處理方式。
13. **客服回覆範例**：提供可修改後直接使用的標準話術。
14. **目前系統差異**：只記錄 Mock 或已知 Bug，不改變正式說法。
15. **待產品確認**：集中列出尚未定案的項目。
16. **截圖預留**：標記日後需要補上的畫面與截圖條件。

## 7. 情境描述標準

每個重要流程至少要涵蓋以下情況：

- 首次使用。
- 已登入與未登入。
- 輸入空值。
- 輸入格式不符。
- 超過或低於限制。
- 重複操作。
- 使用者主動取消或返回。
- 系統處理中、逾時或網路中斷。
- 條件不足，例如餘額、VIP、資格或綁定資料不足。
- 成功後的狀態變化。
- 失敗後是否需要重試，以及重試前要先確認什麼。

涉及金錢、點數、帳號權限或個人資料的功能，必須再補充：

- 是否會預扣、凍結、退回或重新入帳。
- 交易或案件狀態如何判讀。
- 玩家需要提供哪些可公開識別資訊。
- 客服不得要求玩家提供哪些敏感資訊。

## 8. 客服與營運處理原則

客服說明應以「確認現象 → 判斷條件 → 提供處理 → 說明後續」的順序進行。

客服可要求玩家提供：

- 官網頁面或功能名稱。
- 發生時間與時區。
- 畫面顯示的錯誤訊息。
- 操作步驟與是否能重現。
- 使用裝置、瀏覽器與網路環境。
- 帳號或玩家識別資訊，但應依公司身分驗證政策處理。
- 涉及交易時的訂單編號或交易編號。

客服不得要求或記錄：

- 玩家完整密碼。
- 簡訊或雙重驗證的一次性驗證碼。
- 第三方社群帳號密碼。
- 玩家未必要提供的完整支付卡號或安全碼。

客服不得為了讓玩家繼續操作而承諾：

- 一定可以恢復帳號。
- 一定可以補發、退回或增加點數。
- 一定可以取消已完成或已進入不可逆狀態的交易。
- 未經正式規則允許的例外處理。

## 9. 版本與審核流程

每一章採用以下狀態：

| 狀態 | 意義 |
|---|---|
| 草稿 | 已完成初步整理，尚未由產品確認。 |
| 待規則確認 | 流程已寫出，但仍有正式規則或例外情境需要確認。 |
| 已確認 | 產品規則與文字已確認，可作為內部使用版本。 |
| 待截圖 | 文案已確認，等待補上實際畫面。 |
| 發布版 | 已整合至內部網頁與 PDF。 |
| 已過期 | 因產品規則或畫面變更，不再作為現行依據。 |

每章的確認流程：

1. 依正式規格完成初稿。
2. 標記目前 Mock 差異與待確認事項。
3. 由產品負責人確認規則與例外處理。
4. 依確認結果修正文案。
5. 標記章節狀態為「已確認」。
6. 全部章節完成後，再補截圖與版面設計。
7. 產出內部網頁與 PDF，並保留版本日期與變更紀錄。

未經確認的章節可以供內部討論，但不可當作客服正式話術或對外公告來源。

## 10. 網頁、PDF 與截圖規劃

初期以 Markdown 作為唯一內容來源，先完成純文字與規則確認。後續再由同一份已確認內容產出：

- 內部使用網頁：極簡、乾淨、容易搜尋，使用單一強調色與清楚的層級，不大量使用 Emoji 或多色文字。
- PDF：保留章節目錄、頁碼、版本資訊、情境表格與客服快速查詢內容。
- 截圖：以實際正式產品畫面為準，不使用目前 Mock 的測試畫面作為最終操作證據。

截圖需補充以下資訊：

- 截圖名稱與對應章節。
- 操作步驟編號。
- 截圖當下的前置條件。
- 是否需要遮蔽帳號、手機、訂單或其他個人資料。
- 若畫面會因會員等級、活動或狀態不同而變化，需註明適用情境。

## 11. 待確認事項管理

待確認事項不可散落在正文中。每一項應記錄：

- 問題描述。
- 影響章節。
- 目前可確認的內容。
- 不能自行推論的原因。
- 需要由誰確認。
- 確認後需要更新的文件與話術。

目前已知需要持續追蹤的項目包括：

- 公開忘記密碼流程的正式 API、驗證碼有效期限與重發規則。
- 訪客登入是否保留為正式功能。
- 手機驗證碼登入是否保留，以及正式支援的國碼範圍。
- 第三方登入未註冊時的正式補資料流程。
- 註冊成功後是否自動登入。
- 暱稱的完整字元限制與最大長度。
- 密碼允許字元、最大長度、嘗試次數與鎖定規則。
- 帳號重複、停權、凍結與登入失敗的正式錯誤碼及文案。
- 年齡確認的保存期限與「下次不再提示」的正式語意。
- 會員條款、隱私政策與條款版本的正式內容。

## 12. 交接檢查清單

交接人員接手本手冊時，應先確認：

- 是否閱讀本規範文件。
- 是否了解正式規則與 Mock 行為的差異。
- 是否能辨識「正式規則」與「待產品確認」標籤。
- 是否知道本手冊不包含營運後台操作。
- 是否知道敏感資訊不可向玩家索取。
- 是否能依章節中的情境矩陣判斷一般問題與升級問題。
- 是否確認目前使用的是最新發布版本。
