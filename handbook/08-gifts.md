# 第八章：贈禮功能

- 章節狀態：草稿，待產品確認
- 版本：0.1
- 建立日期：2026-08-01
- 適用對象：產品營運人員、客服人員
- 對應功能：贈禮申請、收禮確認、接受、拒絕、取消、逾期、保險箱預扣、VIP 手續費
- 相關章節：第五章「錢包與遊戲幣別」、第七章「金庫、幣別兌換與資金轉移」、第十三章「客服問題回報與案件處理」

## 1. 本章目的

本章說明玩家如何送出贈禮申請、收禮者如何接受或拒絕、送禮者如何取消，以及申請逾期時如何處理預扣資產。內容也定義贈禮手續費、VIP 費率快照、每日次數與單筆上限，讓客服能正確處理「對方沒收到」、「拒絕後金幣去哪裡」、「為什麼收到的金額比較少」等問題。

本章的核心原則是：

> 贈禮採雙向確認，不是直接轉帳。送禮者建立申請時，金額會先從送禮者保險箱預扣；收禮者接受後，扣除申請建立時凍結的 VIP 手續費，實際收到的淨額入帳收禮者主錢包；收禮者拒絕、送禮者取消或申請逾期時，原始預扣金額全額退回送禮者保險箱。

## 2. 重要名詞

| 名詞 | 定義 |
|---|---|
| 贈禮申請 | 送禮者提出、等待收禮者處理的贈禮要求。 |
| 送禮者 | 建立贈禮申請並提供原始金額的玩家。 |
| 收禮者 | 收到申請、可以接受或拒絕的玩家。 |
| 預扣／保留 | 建立申請時，從送禮者保險箱暫時保留完整原始金額，避免被重複使用。 |
| VIP 費率快照 | 建立申請當下依送禮者正式 VIP 等級取得的費率與手續費結果，之後不因 VIP 變動而改變。 |
| 實際收到 | 接受後入帳收禮者主錢包的淨額，等於原始金額扣除手續費。 |
| 逾期 | 申請在有效期限內沒有接受、拒絕或取消，期限到達後進入 `EXPIRED`。 |

## 3. 正式贈禮規則

### 3.1 雙向確認機制

正式流程為：

1. 送禮者建立申請。
2. 原始金額從送禮者保險箱預扣。
3. 收禮者查看申請內容。
4. 收禮者選擇接受或拒絕；送禮者在待處理期間可以取消。
5. 申請接受、拒絕、取消或逾期後，進入不可重複處理的終結狀態。

APP 原型中曾有「直接轉帳、立即到帳」的流程，已不採用，不得作為官網正式說法，也不得以「小額可直接轉、大額才需要確認」的方式自行創造雙軌規則。

>
> - 放置位置：本節雙向確認流程之後。
> - 用途：確認建立申請、保險箱預扣、收禮者接受／拒絕與送禮者取消的入口，不呈現直接轉帳流程。
> - 狀態：待補正式產品截圖。

### 3.2 金額、次數與期限

目前正式業務規則為：

- 單筆贈禮上限：1,000,000。
- 每位送禮者每日最多建立 10 次申請。
- 每筆申請有效期限：168 小時，即 7 天。
- 送禮金額必須大於 0，並依整數規則處理。
- 送禮者不得選擇自己作為收禮者。
- 收禮者必須是有效且允許被贈禮的帳號；若玩家被封鎖、帳號無效或不符合資格，系統應拒絕申請。
- 建立申請時需有足夠的送禮者保險箱可用金幣。
- 每日次數依正式產品指定時區判定，目前規格以 Asia/Taipei 為基準。

「每日 10 次」是建立申請的次數上限，不是接受次數，也不是玩家可以同時保留的無限待處理工單。若後端另設定同時進行中的上限，應以正式錯誤回應與產品公告為準。

> - 用途：確認單筆上限、今日剩餘次數、有效期限、時區與超過限制的提示。

### 3.3 手續費與 VIP 費率快照

贈禮手續費不採全站固定 5%，而是依送禮者建立申請當下的 VIP 等級費率計算。

正式概念如下：

```text
手續費 = floor(原始贈禮金額 × 建立申請時的 VIP 費率)
實際收到 = 原始贈禮金額 - 手續費
```

其中：

- `floor` 代表無條件捨去小數。
- 建立申請時要保存 VIP 費率、手續費與實際收到金額的快照。
- 申請等待期間，即使送禮者 VIP 等級改變，這筆申請仍使用原先快照。
- 接受時，收禮者主錢包收到實際收到金額。
- 拒絕、取消或逾期時，送禮者保險箱退回完整原始金額，不因手續費先行扣除而少退。
- 正式 API 必須明確定義費率單位，不可混用 `5` 與 `0.05` 的表示方式。

各 VIP 等級的實際費率數值與費率單位尚未在產品規格中完成定案，因此客服不能引用目前 Mock 的固定 5% 作為正式承諾。

## 4. 贈禮申請流程：送禮者

### 4.1 建立前確認

1. 玩家登入官網。
2. 進入贈禮入口，查看今日剩餘次數、單筆上限與目前 VIP 贈禮費率。
3. 確認保險箱有足夠可用金幣。
4. 選擇收禮者。
5. 確認收禮者不是自己，且不是無效、封鎖或禁止接收贈禮的對象。

如果玩家選不到某位對象，不代表可以用暱稱自行建立申請。應以系統提供的有效玩家選項與收禮資格為準。

> **截圖預留｜08-4.1-01｜建立前額度、收禮者與資格檢查**
>
> - 放置位置：本節建立前確認流程之後。
> - 用途：確認今日剩餘次數、單筆上限、VIP 費率、保險箱餘額、收禮者清單與無效／封鎖對象提示。
> - 狀態：待正式資格規則確認後補截圖。

### 4.2 填寫與確認

1. 輸入贈禮金額。
2. 系統檢查金額是否為正整數、未超過 1,000,000，且不超過保險箱可用餘額。
3. 系統顯示原始金額、VIP 費率、手續費與收禮者實際收到金額。
4. 系統顯示申請有效期限與預計逾期時間。
5. 玩家確認送禮者、收禮者、金額與費率快照。
6. 玩家按下送出申請。

建立前若頁面重新整理、VIP 狀態更新、跨裝置操作或費率資料過期，應重新查詢贈禮額度與正式費率。建立後則以訂單／申請中的費率快照為準。

### 4.3 建立成功後

- 申請狀態為 `PENDING`。
- 原始贈禮金額從送禮者保險箱預扣或保留。
- 送禮者當日已使用次數增加一次。
- 收禮者收到待處理通知或在贈禮列表看到申請。
- 送禮者可查看申請內容與狀態。
- 送禮者在收禮者處理前可以取消。

## 5. 贈禮流程：收禮者

### 5.1 查看申請

1. 收禮者登入官網。
2. 開啟通知、贈禮列表或會員相關入口。
3. 查看送禮者、原始金額、VIP 費率快照、手續費、實際收到金額與到期時間。
4. 確認是否接受該筆贈禮。

收禮者不需要先付款，也不應被要求提供密碼、付款資料或驗證碼來「領取贈禮」。任何要求玩家私下匯款才能收禮的說法，都不是本功能正式流程。

> **截圖預留｜08-5.1-01｜收禮者查看待處理申請**
>
> - 放置位置：本節查看申請流程之後。
> - 用途：確認送禮者、原始金額、費率快照、手續費、實收金額、期限與接受／拒絕入口。
> - 狀態：待補正式產品截圖。

### 5.2 接受

1. 收禮者開啟待處理申請。
2. 再次確認送禮者、原始金額、手續費與實際收到金額。
3. 按下「接受」。
4. 系統確認申請仍為 `PENDING` 且尚未逾期、取消或被其他操作處理。
5. 系統將實際收到金額入帳收禮者主錢包。
6. 申請狀態變更為 `ACCEPTED` 或正式對應的完成狀態。
7. 送禮者的原始預扣金額完成結算，不再退回保險箱。
8. 雙方可在贈禮列表或交易紀錄查看結果。

接受後，收禮者收到的是扣除手續費後的淨額；送禮者不能因看到原始金額與收禮者實際收到不同，就主張系統少轉，前提是費率快照與計算正確。

> **截圖預留｜08-5.2-01｜收禮者接受確認與入帳結果**
>
> - 放置位置：本節接受流程之後。
> - 用途：確認接受前的二次確認、淨額入帳、`ACCEPTED` 狀態與雙方交易紀錄入口。
> - 狀態：待補正式產品截圖。

### 5.3 拒絕

1. 收禮者開啟 `PENDING` 申請。
2. 確認不接受本次贈禮。
3. 按下「拒絕」。
4. 系統將申請狀態變更為 `REJECTED`。
5. 送禮者原先預扣的完整原始金額退回送禮者保險箱。
6. 收禮者不會收到任何金額，也不應產生贈禮手續費。

拒絕不是把金額退到收禮者帳戶，也不是把金額直接轉給其他人。退款對象固定為原送禮者的保險箱。

> **截圖預留｜08-5.3-01｜收禮者拒絕與送禮者全額退款狀態**
>
> - 放置位置：本節拒絕流程之後。
> - 用途：確認拒絕前提示、`REJECTED` 狀態、收禮者不入帳與送禮者保險箱全額退回。
> - 狀態：待補正式產品截圖。

## 6. 取消與逾期流程

### 6.1 送禮者取消

在收禮者尚未接受或拒絕前：

1. 送禮者開啟自己的待處理申請。
2. 確認申請仍為 `PENDING`。
3. 按下「取消」。
4. 系統將狀態變更為 `CANCELLED`。
5. 原始贈禮金額全額退回送禮者保險箱。

若收禮者已接受、已拒絕或申請已逾期，送禮者不能再用取消動作改變結果。

> **截圖預留｜08-6.1-01｜送禮者取消 PENDING 申請與退款**
>
> - 放置位置：本節取消流程之後。
> - 用途：確認取消前狀態檢查、`CANCELLED` 結果與原始金額退回送禮者保險箱。
> - 狀態：待補正式產品截圖。

### 6.2 168 小時逾期

1. 申請建立後開始計算 168 小時有效期。
2. 若期限內沒有接受、拒絕或取消，申請進入 `EXPIRED`。
3. 原始預扣金額全額退回送禮者保險箱。
4. 收禮者不能再接受已逾期申請。
5. 送禮者不能再取消已逾期申請。

逾期退款應由後端排程或讀取時的正式後端判定完成。客服不可告訴玩家必須一直開著瀏覽器才能退款，也不可用前端輪詢是否執行作為正式規則。

> **截圖預留｜08-6.2-01｜168 小時逾期與全額退款狀態**
>
> - 放置位置：本節逾期流程之後。
> - 用途：確認倒數／到期時間、`EXPIRED` 狀態、接受按鈕停用與送禮者保險箱退款結果。
> - 狀態：待後端排程與玩家可見時間規則確認後補截圖。

## 7. 贈禮狀態機

| 狀態 | 可以由誰操作 | 下一步 | 金額結果 |
|---|---|---|---|
| `PENDING` | 收禮者接受／拒絕；送禮者取消 | `ACCEPTED`、`REJECTED` 或 `CANCELLED` | 原始金額仍在送禮者保險箱預扣 |
| `ACCEPTED` | 不可再次處理 | 終結 | 淨額入收禮者主錢包；原始預扣結算 |
| `REJECTED` | 不可再次處理 | 終結 | 原始金額全額退送禮者保險箱 |
| `CANCELLED` | 不可再次處理 | 終結 | 原始金額全額退送禮者保險箱 |
| `EXPIRED` | 不可再次處理 | 終結 | 原始金額全額退送禮者保險箱 |

同一筆申請若同時有兩邊操作，後端應以狀態鎖定、冪等與正式時間順序決定唯一結果。玩家若看到按鈕成功但列表未更新，不要重複點擊，應先查詢申請狀態。

## 8. 金額流向範例

假設送禮者建立一筆原始金額為 `A` 的申請，建立當下 VIP 費率為 `r`：

```text
建立申請：送禮者 vault.gold - A
手續費：floor(A × r)
接受後：收禮者 gold.stored + (A - floor(A × r))
```

如果收禮者拒絕、送禮者取消或申請逾期：

```text
送禮者 vault.gold + A
收禮者不入帳
```

這個流程表示手續費只會影響接受後收禮者收到的淨額；在申請未接受前，送禮者預扣的是完整原始金額。VIP 等級在等待期間改變，也不會回溯修改已建立申請的費率。

> - 狀態：待正式 VIP 費率確認後補截圖。

## 9. 常見情境與處理矩陣

| 玩家情況 | 玩家可能看到的結果 | 客服第一步 | 後續處理 |
|---|---|---|---|
| 未登入使用贈禮 | 開啟登入或無法查看 | 引導完成登入 | 登入後重新查詢額度與申請 |
| 選不到收禮者 | 對象不在清單或顯示無效 | 確認對象帳號與互動資格 | 不以暱稱自行建立，依有效玩家資料處理 |
| 想送給自己 | 顯示不可送給自己 | 說明收禮者不可與送禮者相同 | 不建立例外流程 |
| 保險箱餘額不足 | 送出按鈕停用或餘額不足 | 確認可用的是保險箱金幣 | 引導先存入或取得符合規則的金幣 |
| 超過單筆 1,000,000 | 顯示超過上限 | 說明單筆上限 | 拆成多筆仍須遵守每日次數，不可保證可行 |
| 當日已建立 10 次 | 顯示每日次數已達上限 | 確認 Asia/Taipei 日期與已用次數 | 等待下一個正式日或依公告處理 |
| 對方尚未處理 | 狀態 `PENDING` | 說明對方需接受或拒絕 | 送禮者可在期限內取消 |
| 收禮者接受後收到較少 | 實收金額扣除手續費 | 查建立時 VIP 費率快照與計算 | 計算正確則說明淨額；不以固定 5% 解釋 |
| 收禮者拒絕 | 狀態 `REJECTED` | 說明原始金額退回送禮者保險箱 | 查退款流水，不是退給收禮者 |

| 逾期後收禮者仍想接受 | 接受按鈕停用或失敗 | 說明逾期申請不可接受 | 若退款未完成，升級查詢，不重新改狀態 |
| 送禮者 VIP 在等待中升級 | 玩家要求重新計算手續費 | 查申請建立時快照 | 以原快照結算，不回溯調整 |
| 玩家重複按接受 | 顯示狀態已變更或重複錯誤 | 查申請最終狀態 | 以唯一正式結果為準，不重複入帳 |
| 收禮者沒有收到通知 | 申請仍在贈禮列表 | 先查申請是否成功建立 | 通知缺失與資產狀態分開處理，必要時升級 |

| 玩家要求直接轉帳 | 想跳過對方確認 | 說明平台採雙向確認 | 不提供直接轉帳例外流程 |
| 玩家要求用銅幣或活動卡贈禮 | 系統不允許或沒有選項 | 確認贈禮來源為保險箱金幣 | 依正式資產種類說明，不自行轉換 |

## 10. 客服檢查清單

贈禮案件至少確認：

1. 送禮者與收禮者帳號識別資訊。
2. 申請編號與目前狀態。
3. 建立時間、當地日期與 168 小時期限。
4. 原始贈禮金額。
5. 建立申請時的 VIP 等級與費率快照。
6. 手續費、實際收到金額與整數計算結果。
7. 送禮者保險箱預扣、接受入帳或退款流水。
8. 每日已用次數與適用時區。
9. 收禮者是否接受、拒絕、取消或逾期。
10. 玩家是否重複操作或跨裝置操作。
11. 通知是否收到，但不要把通知缺失直接當成資產失敗。
12. 畫面錯誤訊息與必要截圖。

## 11. 客服可直接處理與升級條件

### 11.1 可直接處理

- 說明贈禮不是直接轉帳，而是申請後由收禮者確認。
- 說明單筆 1,000,000、每日 10 次與 168 小時有效期限。
- 引導送禮者查看保險箱預扣與贈禮申請狀態。
- 說明接受後收禮者收到扣除 VIP 手續費的淨額。
- 說明拒絕、取消與逾期會把完整原始金額退回送禮者保險箱。
- 引導雙方查看申請列表與交易紀錄。

### 11.2 必須升級

- 申請狀態已接受，但收禮者主錢包沒有淨額入帳。
- 申請拒絕、取消或逾期，但送禮者保險箱沒有全額退款。
- 同一申請同時出現接受與拒絕，或兩次入帳／退款。
- VIP 費率快照缺失、單位不明或計算與正式規則不一致。
- 未到 168 小時就被標記過期，或已過期仍可接受。
- 未超過上限卻被錯誤擋下，或超過上限仍成功建立。
- 每日次數、時區或重置時間判定錯誤。
- 玩家沒有建立申請卻出現 `P2P_OUT`，或沒有接受卻出現 `P2P_IN`。
- 對象資格、封鎖狀態與畫面可選名單不一致。

### 11.3 禁止事項

- 不得要求收禮者先付款、提供付款資料或交出驗證碼。
- 不得把目前 Mock 固定 5% 費率說成正式 VIP 費率。
- 不得承諾客服可以直接幫玩家接受、拒絕或修改贈禮申請。
- 不得將拒絕／取消／逾期的退款說成退到收禮者帳戶。
- 不得在狀態未查明前要求玩家重送或重複接受。
- 不得要求玩家提供密碼或其他敏感身分驗證資料。

## 12. 客服回覆範例

### 送禮者詢問「對方為什麼還沒收到？」

> 贈禮採雙向確認機制，建立申請後需要由收禮者在有效期限內接受。請提供申請編號，我們會先確認目前是待處理、已接受、已拒絕、已取消或已逾期。待處理期間，原始金額會先保留在送禮者保險箱，不代表已直接入帳收禮者帳戶。

### 收禮者詢問「為什麼收到的金額比較少？」

> 接受贈禮後，收禮者收到的是扣除送禮者建立申請時 VIP 費率所計算的手續費後的淨額。請查看該筆申請的費率快照、原始金額、手續費與實際收到金額；VIP 等級在等待期間變動，不會回溯修改這筆申請。

### 送禮者詢問「對方拒絕後，錢會去哪裡？」

> 收禮者拒絕後，原始贈禮金額會全額退回原送禮者的保險箱，不會轉給收禮者，也不會自動轉給其他帳號。若列表已顯示拒絕但保險箱尚未更新，請提供申請編號，我們會查退款流水。

### 玩家詢問「可以不要對方同意，直接轉帳嗎？」

> 目前正式贈禮流程是申請後由收禮者接受或拒絕，不提供直接轉帳或跳過確認的例外流程。請依贈禮申請畫面操作，並在送出前確認收禮者與金額。

### 玩家詢問「贈禮手續費是不是固定 5%？」

> 贈禮手續費依送禮者建立申請當下的 VIP 等級費率計算，不是全站固定 5%。正式費率與本次申請的費率快照會以贈禮確認畫面及申請明細為準。

## 13. 目前系統差異

以下只供內部理解前端 Mock，不可取代正式規則：

- 目前前端以固定 5% 作為贈禮費率預設值；正式規則改為 VIP 分級費率，並在建立申請時凍結快照。
- 目前贈禮狀態與餘額主要由瀏覽器工作階段模擬，重新整理可能重置測試資料；正式狀態應由後端保存。
- 目前前端以本地輪詢模擬逾期處理；正式逾期判定與退款應由後端排程或正式查詢處理，不能要求玩家保持頁面開啟。
- 目前已知前端在「收禮者拒絕」的某些情況下沒有正確執行送禮者退款；正式規則必須是拒絕後將完整原始金額退回送禮者保險箱。此差異應列為修正項，不得寫成正式流程。
- 目前畫面可能只展示測試贈禮資料，不能由測試清單推論正式玩家能看到的申請數量或通知方式。
