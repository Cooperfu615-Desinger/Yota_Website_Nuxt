  1. 贈禮流程 → 統一為雙向確認（官網現況，APP 需補流程）
  2. 儲值幣別通道 → 維持平台差異，不強制統一
  3. 遊戲分類數量 → 本階段只統一資料結構，範圍留待營運/採購階段決定
  4. VIP 結構化門檻 → 官網補齊結構化（比照 APP VIP_LEVEL_RULES）
  5. 金額／點數 → 整數、小數捨去；台1＝金1＝銀100；銅幣無價值；無外部提款
  6. 贈禮費率 → 依 VIP 分級並在建立申請時凍結；有效流水由 Gordan × Hulk 共同定義

20-frontend.md 以此決策為準撰寫，不再重複列現況分岔。

  1. 玩家進入會員中心的獎勵卡分頁。
  2. 系統列出目前可見卡片與每張卡的狀態、餘額、門檻及期限。
  3. 玩家可啟用卡片；已啟用卡片依遊戲／財務規則累積活動餘額。
  4. 符合條件時可選取至少兩張卡進行合併；合併後來源卡標為 merged，新卡為 inactive。
  5. 玩家完成流水後進行轉換，系統以 min(currentBalance, conversionLimit) 計算可轉換額度，剩餘額度依規則回收。

7. 主要流程：優惠碼預覽與兌換

  1. 未登入玩家點擊兌換區，應開啟登入／註冊並保留原目的地。
  2. 已登入玩家輸入最多 8 碼的大寫英數字串；前端先正規化並顯示預覽。
  3. 預覽需指出活動名稱、獎勵類型、數量、有效期限與是否已兌換。
  4. 玩家確認後才呼叫兌換動作；成功後更新對應活動餘額、錢包或獎勵卡。
  5. 成功、格式錯誤、無效、過期、已使用、不可兌換與處理失敗均需可辨識，且不能因重複點擊重複發獎。

8. 主要流程：玩家贈禮申請

  1. 玩家從保險箱轉帳分頁或聊天玩家小卡選取收件人。
  2. 輸入贈禮幣別與金額；前端先驗證收件人、金額正數、可用餘額與每日上限。
  3. 預覽頁顯示原額、手續費、收件人實收額與目前 VIP 費率快照。
  4. 確認後從送禮者保險箱保留資產，建立待處理申請。
  5. 收件人接受、拒絕，或送禮者取消；逾期案件進入 expired，應依規則退回保留額。

目前原型：單一玩家每日最多 10 筆、單筆上限 1,000,000，申請有效期 168 小時；這些值需在後端契約與營運設定確認後才可視為正式規則。

9. 例外、錯誤與不可操作狀態

  • 優惠碼為空、長度超過 8、包含非英數字、無效、已使用或已過期時，不進入確認狀態。
  • Guest 不得兌換優惠碼，也不應在未識別會員的情況下建立可領取贈禮。
  • 餘額不足、金額低於最小單位、收件人不存在、自己送給自己、達到每日上限時，送出按鈕應阻擋並提供原因。
  • 到期前最後 72 小時的獎勵卡不可合併但仍可啟用；不可操作卡片需保留原因說明。
  • 任一錢包更新失敗時，兌換／贈禮應回滾或進入可查詢的待處理狀態，不可只更新畫面。

10. 合併、費率與資產一致性規則

目前 Web 合併規則為至少兩張、無固定張數上限，僅允許 inactive 或距離到期超過 72 小時的 paused 卡片；新卡取最早到期日，餘額、流水門檻與轉換上限依目前工具相加，來源卡標記為 merged，新卡仍可再合併。

贈禮手續費依送禮者 VIP 等級計算，預覽需固定本次費率快照；服務端應以交易建立時的快照為準。所有資產變更都需要交易 ID、來源、時間與可追溯的前後餘額。

11. 權限、安全與風控邊界

  • 只有已驗證登入會員能兌換優惠碼、啟用／轉換獎勵與建立贈禮。
  • 會員只能讀取自己的卡片、兌換紀錄、錢包與贈禮案件；只能在授權狀態下讀取收件人公開識別。
  • 優惠碼兌換必須由服務端做原子性的一次性消費，前端 claimsByMember 僅是 Mock。
  • 贈禮需有防刷、速率限制、黑名單／停權檢查、重複請求去重與客服稽核能力。
  • 金額不可由前端決定；前端顯示的 VIP 費率、餘額與到期日都不是授權依據。

12. API、事件與目前缺口

需要補定的事件：reward.claimed、reward-card.activated、reward-card.merged、reward-card.converted、gift-request.created、gift-request.resolved。所有事件需可與信箱、通知、客服查詢與財務對帳關聯。

3. 每日簽到的介面結構

每日任務頁以 31 天日曆／進度視覺為核心，需呈現當日日期、連續進度、每日獎勵、里程碑標記、今日操作與補簽入口。已完成、今日可簽、今日待處理、漏簽、未開始等狀態要有不同視覺與可操作性。

4. 每日任務資料與狀態

目前每日獎勵由 siteContent.dailyCheckin.dailyRewards 提供，共 31 天；里程碑為第 5、7、10、15、20、25、30 天；補簽成本為每日 100。頁面目前以 useState 保存已簽天數與已領里程碑，重新整理／換裝置不代表正式持久化。

狀態模型至少包含：日期序號、日曆日期、是否已簽、是否為今天、是否可補簽、是否已領里程碑、獎勵內容與處理狀態。正式服務需另提供伺服器時間、連續簽到計算與不可竄改的領取紀錄。

5. 每日簽到主要流程

  1. 玩家進入 /lobby/daily，系統取得伺服器時間與本期簽到資料。
  2. 玩家點擊今日簽到；未登入時先要求登入。
  3. 成功後更新今日狀態、金幣／獎勵卡餘額與里程碑進度。
  4. 若有可領里程碑，玩家可逐項領取並看到成功提示；不可重複領取。
  5. 玩家可查看漏簽日，選取符合條件的日期進行補簽；補簽前需顯示成本與確認。

6. 補簽、里程碑與差異標記

補簽必須驗證玩家餘額、可補日期、活動期間、每日／整期限制與重複請求。扣除成本與補發獎勵需是同一筆可追蹤交易。

目前 siteContent.ts 的第 10／15／20 天標示為活動銀幣獎勵，而 useRewardCardState.ts 另以活動銀幣獎勵卡定義；舊的前端敘述曾出現不同幣別說法。Web 規格暫以現行程式來源標為「待正式規則封存」，不可在 Figma 或 API 任一側自行定案。

7. 活動列表與活動詳情

活動列表需提供進行中、即將開始、已結束等狀態分組或篩選，活動卡顯示主視覺、標題、副標、獎勵、截止時間與是否為儲值相關活動。活動詳情需列出資格、玩法、期間、獎勵發放、導流按鈕與注意事項。

目前 siteContent.events 是靜態資料，含 active、upcoming、ended 與 deposit 標記；未來需由 CMS／活動服務提供時間與資格，不應以瀏覽器時鐘單獨判定活動狀態。

8. 排行榜資訊架構

排行榜提供「倍數榜」「贏分榜」「富豪榜」三個 Tab。每個榜單至少有前三名視覺、後續列表、玩家名稱／識別、成績、遊戲或來源與更新／活動期間說明。若登入，應提供「我的排名」或清楚說明目前未提供該功能。

目前 siteContent.leaderboard 提供 preview、top3 與 rest 靜態資料；Web 版需明確標示這是原型資料，不能讓玩家誤認為即時獎金或結算結果。

9. 排行榜流程與例外

玩家可切換榜單、查看排名內容、由活動卡導向榜單。載入中、暫無資料、活動未開始、活動已結束、服務錯誤與玩家未上榜需各有狀態。榜單數字需固定千分位、正負號與幣別／倍率格式。

WEB SPEC 10｜社交互動、聊天與客服

文件狀態：Phase 2 初版，已依目前 Nuxt 原型整理；即時通訊、客服後台與風控仍待正式化。 工作單映射：YOTAPLATFO-456（SPEC）／YOTAPLATFO-469（Figma）／YOTAPLATFO-482（WEB／Nuxt） APP 參考：APP 11「社交互動與客服」；本文件以 Web 聊天頁的三頻道與客服案件模型為準。

0. 文件狀態與範圍

本分冊描述 /lobby/chat 的世界頻道、私人頻道、客服頻道，以及玩家清單、玩家小卡、加好友、黑名單、贈禮導流、檢舉與客服案件對話。社交功能目前為前端 Mock；客服狀態雖已抽成共用 useState，仍未與客服後台或 WebSocket 連接。

1. 產品目標與使用情境

  • 玩家可在世界頻道閱讀與發送訊息，從在線玩家清單查看公開資訊。
  • 玩家可從公開玩家資訊發起私人對話、加好友、封鎖、檢舉或前往贈禮／轉帳。
  • 玩家可在客服頻道建立問題、查看案件、繼續對話、讀取未讀回覆。
  • 所有社交與客服操作都要有清楚的可見範圍、權限與失敗原因，不能把 Mock 成功誤認為服務端已受理。

2. 頻道與資訊架構

聊天頁提供三個 Tab：

頻道 目前來源 主要功能
世界頻道 siteContent.chat.worldMessages，頁面區域 Mock 公開聊天、點擊訊息中的玩家名稱查看玩家卡
私人頻道 siteContent.chat.privateConversations，頁面區域 Mock 對話列表、主從導覽、私人訊息、封鎖提示
客服頻道 useSupportTicketState，跨元件 useState 提問紀錄、類別選擇、案件對話、未讀與結案

目前頻道可由 ?channel=world|private|support 深連結，世界頻道會移除 query；切換頻道需同步 URL 且不應遺失各頻道草稿／清單上下文。

3. 世界頻道流程

玩家進入頁面後可閱讀世界訊息，輸入訊息並送出；點擊可識別玩家名稱會開啟玩家小卡。世界訊息與線上玩家清單目前為 seed data，送出只更新當前頁面的 ref，重新整理即回到初始資料。

世界頻道需預留載入、連線中斷、慢速、訊息發送失敗、禁言、頻率限制、內容審核與歷史訊息載入狀態。正式版不可只依賴瀏覽器 push 來視為成功。

4. 玩家清單與玩家小卡

世界頻道可開啟玩家清單抽屜。玩家小卡顯示名稱、帳號／玩家識別、VIP、等級、在線狀態、簡介與近期遊戲；目前名單取自 siteContent.chat.onlinePlayers 與私人對話對象。

玩家小卡操作包含：發起私人訊息、加好友、加入黑名單、檢舉、贈禮與轉帳。被封鎖玩家不能查看小卡、私訊或繼續社交操作；封鎖後要關閉目前小卡與清單並顯示結果。

5. 私人頻道流程

  1. 玩家從私人頻道清單選取對話，進入主從對話畫面。
  2. 若由玩家小卡發起且沒有既有對話，建立當前頁面的新對話。
  3. 未封鎖對象可送出訊息；封鎖對象顯示唯讀提示。
  4. 開啟對話時清除該對話的頁面內未讀數；返回後保留對話清單。

正式版需要定義對話建立、訊息送達／已讀、撤回、刪除、封鎖同步、多裝置與離線重連。現行私人對話不是服務端持久化資料。

6. 好友、黑名單與玩家關係

useSocialState.ts 目前以 useState 保存好友與黑名單；初始好友來自 onlinePlayers.isFriend，新增／移除好友與封鎖／解除封鎖只在本次瀏覽工作階段有效。封鎖玩家會同步移除好友關係。

正式規格需補上好友請求或直接加好友的產品決策、關係狀態、雙向／單向可見性、黑名單同步、解除封鎖後能否恢復好友與關係變更通知。

7. 玩家檢舉流程

玩家可從玩家小卡開啟檢舉 Modal，填寫原因與補充說明。送出後目前會建立客服 report 類別案件，第一則訊息包含檢舉對象、帳號、原因與補充內容，並切換至客服頻道的案件對話。

檢舉對象必須具有有效 playerId、account、name；空原因、無效對象或已達進行中客服案件上限時不得建立案件。正式版需加上內容證據、時間戳、重複檢舉合併、申訴與後台處理結果。

8. 客服頻道與案件列表

客服頻道採「案件清單 → 類別選擇／草稿 → 案件對話」主從流程。清單可顯示全部、進行中、已結案篩選、案件 ID、類別、最後訊息、更新時間與未讀數。點開案件會先清除未讀。

目前 useSupportTicketState.ts 限制同時最多 1 筆進行中的案件；種子案件為 CS-000001，類別資料由 supportQuestionCategories 提供，共 7 類。

9. 客服建立與對話流程

  1. 玩家按「新增提問」，若已有進行中案件，顯示上限提示。
  2. 從 7 個類別中選取帳號、儲值／付款、帳務／訂單、遊戲／結算、活動／獎勵、保險箱／贈禮或檢舉玩家等類別。
  3. 草稿頁只在送出第一則非空訊息後建立案件；離開草稿不留下紀錄。
  4. 進行中案件可繼續發訊息；已結案案件唯讀，並可建立新提問。
  5. 客服回覆會增加未讀數；正式服務收到回覆時需透過即時事件或重新整理同步。

10. 客服狀態、訊息與例外

案件目前至少有 ongoing／closed 狀態；訊息有玩家／客服發送者、時間、文字與未讀計數。空訊息、無效類別、找不到案件、已結案、超過案件上限等錯誤需可轉換為使用者可理解的提示。

已結案案件不得再送訊息；客服頻道本身的未讀 badge 要顯示總未讀，超過 99 顯示 99+。刪除、封存、附件、圖片、敏感資料遮罩與案件 SLA 尚未在目前 Web 原型中定義。

11. 權限、內容安全與使用者保護

  • 世界頻道發言需有登入、年齡門檻、禁言／封鎖／頻率限制與內容審核策略。
  • 私人訊息只對發送者與收件者可見；封鎖關係需在服務端生效，不能只靠前端 isBlockedPlayer。
  • 檢舉內容與客服案件可能含個資或敏感資料，須限定客服角色、保存期限、稽核與遮罩範圍。
  • 贈禮與轉帳只提供導流，不得因聊天頁操作繞過財務權限與交易確認。

12. API、WebSocket 與目前缺口

API gap analysis 已列出 WebSocket、好友、世界頻道、玩家目錄、私訊與檢舉／客服後台等缺口。目前世界／私人頻道仍是頁面 Mock，客服的 receiveSupportMessage 只是為未來 API／WebSocket 預留的本地函式。

正式化需定義連線認證、頻道訂閱、訊息序號、重連與去重、已讀游標、案件事件、推播通知、內容審核結果與客服後台回覆格式。

13. Figma 交付內容

Figma 需交付三頻道 Tab、世界訊息串、在線玩家抽屜、玩家小卡、私人對話列表／內容、封鎖後狀態、檢舉 Modal、客服案件列表／篩選、類別選擇、草稿、進行中／結案對話、未讀 badge、空狀態與錯誤提示的桌面／手機版。

需特別標示從玩家小卡進入轉帳與客服檢舉後的導流脈絡，並定義訊息可點擊名稱、玩家身份顯示與敏感資料遮罩。

14. Nuxt 實作邊界

pages/lobby/chat.vue 管理頻道、世界訊息、私人對話與頁面通知；useSocialState.ts 管理好友／黑名單；useSupportTicketState.ts 管理客服案件。使用 ClientOnly 的玩家卡與檢舉 Modal 需繼續遵守 SSG hydration 規則。

不應把頁面 ref 的訊息清單直接升級為跨裝置資料；接入 WebSocket 後需把服務端訊息作為唯一來源，並保留連線中、發送中、失敗與重試狀態。URL channel query 只代表視圖，不代表授權。

WEB SPEC 11｜信箱、通知與設定

文件狀態：Phase 2 初版，已依目前 Nuxt 原型整理；通知服務、偏好同步與帳戶安全仍待正式化。 工作單映射：YOTAPLATFO-457（SPEC）／YOTAPLATFO-470（Figma）／YOTAPLATFO-483（WEB／Nuxt） APP 參考：APP 12「信箱、通知與設定」；Web 以 /lobby/inbox 與 /lobby/settings 的目前實作為基準。

0. 文件狀態與範圍

本分冊涵蓋登入後信箱、系統／營運／帳務訊息、信件附件領取、信件刪除、音樂與音效、語言選擇、黑名單管理、法律文件入口與登出確認。推播、跨裝置同步、批次讀取與服務端通知尚未完成，需與客服、獎勵、財務及帳戶規格協同定義。

1. 產品目標與使用情境

  • 玩家能集中查看平台公告、活動訊息、帳務結果與可領取附件。
  • 玩家能安全領取一次性附件，並在錢包／交易紀錄讀回結果。
  • 玩家能調整音樂、音效、主題與語言流程，管理黑名單並查看條款。
  • 玩家登出前能看懂會離開目前帳戶並返回官網首頁；未登入不可直接取得私人信件。

2. 入口、路由與權限

功能 路由 未登入行為 目前來源
信箱 /lobby/inbox 顯示登入／註冊入口並保留目的地 pages/lobby/inbox.vue
設定 /lobby/settings 由 lobby layout 的登入邏輯保護 pages/lobby/settings.vue
條款／隱私／服務規範 Modal 開啟法律文件 Modal useLegalState.ts、LegalModal.vue

信箱與設定均使用 layout: 'lobby'；AppBottomNav、Header 與側邊導覽的入口狀態需在 web-04-lobby-navigation.md 統一維護。

3. 信箱列表與分類

目前信箱提供「營運公告」與「系統通知」兩個篩選；system 與 deposit 會歸在系統通知，event 歸在營運公告。每筆信件顯示已讀點、類型、時間、標題、預覽與附件標籤。

目前 InboxMessage 類型為 system | event | deposit，種子資料包含活動公告、排行榜活動、儲值到帳確認與維護公告。正式版需補分頁／游標、排序、服務端未讀數、通知保留期限與多語內容。

4. 閱讀、已讀與刪除流程

  1. 玩家切換分類並從列表選取信件。
  2. 開啟時呼叫 markRead，右側／手機詳情顯示完整內容。
  3. 若有附件，顯示附件幣別、數量、領取說明與一次性按鈕。
  4. 玩家可刪除目前信件；刪除後關閉詳情並顯示結果提示。
  5. 返回列表時保留目前分類，不應因讀取信件重置整個列表視圖。

目前沒有批次全讀、批次刪除、封存、搜尋、釘選、撤回或跨裝置已讀同步；這些需由產品決策後再加到工作單／API。

5. 信件附件與獎勵領取

附件目前支援 gold／silver／bronze 錢包獎勵；領取成功後呼叫 addWalletReward，並將 claimed 設為 true，按鈕改為已領取。重複點擊或已領附件不得再次入帳。

正式版的領取結果必須由服務端原子性消費，回傳獎勵交易 ID、實際入帳錢包、失敗原因與可重試狀態。附件可能過期、被撤回、受會員資格限制或需要從獎勵卡／活動服務取得，這些目前尚未在 Web Mock 建模。

6. 信箱狀態與錯誤

需覆蓋登入要求、載入中、空信箱、分類無資料、信件已讀／未讀、附件可領／已領、領取中、領取失敗、信件不存在、已刪除與服務中斷。手機版詳情以 overlay 呈現，關閉後回到列表。

目前 runMock 會等待約 700ms 模擬領取，這是原型互動，不是服務端延遲或 SLA。正式訊息必須避免把 setTimeout 結果當成付款／獎勵完成證據。

7. 設定資訊架構

設定頁目前分四區：

  1. 音樂與音效：背景音樂開關、操作音效試聽與開關。
  2. 語言：繁體中文、English、日本語三個選項；目前只對齊選擇流程，文案仍為繁體中文。
  3. 黑名單管理：顯示封鎖玩家、玩家識別與解除封鎖。
  4. 條款與帳號：會員條款、隱私政策、平台服務規範與登出。

主題目前由偏好狀態保存並套用 document.documentElement.dataset.theme；若正式提供深／淺色主題，需另補完整 token 與可讀性驗證。

8. 偏好狀態與保存

usePreferencesState.ts 提供 musicEnabled、soundEnabled、theme、language、pushEnabled。目前 localStorage key 為 jh_preferences，保存音樂、音效、主題、語言；pushEnabled 目前只在 state 中存在，未納入持久化。

初始化只在 client 端讀取 localStorage，並在設定變更後更新 DOM／localStorage。正式版需決定偏好是否與會員帳戶同步、未登入是否保存、跨裝置優先序與伺服器失敗回退。

9. 黑名單管理流程

玩家從聊天玩家卡加入黑名單後，設定頁可看到清單、頭像、名稱、玩家識別與「解除封鎖」操作。解除後顯示提示；目前關係只保存在本次瀏覽 session，且與 useSocialState.ts 共用。

正式版需定義封鎖對世界頻道、私人訊息、玩家資料、贈禮、轉帳與檢舉的影響，並在服務端同步黑名單，避免設定頁與聊天頁狀態分裂。

10. 法律文件、帳戶與登出

條款、隱私與服務規範從設定頁開啟共用 Legal Modal；內容需與登入／AgeGate 的同意流程一致。登出按鈕開啟確認 Modal，確認後清除登入狀態與受保護頁面資料，返回官網首頁。

正式版需補登入 token／refresh token 撤銷、其他裝置 session、登出失敗、未保存流程、法律版本與同意紀錄。不能只把前端 isLoggedIn 設為 false 就視為安全登出。

11. 通知、未讀與跨功能關聯

信箱附件可能來自活動、儲值、任務、獎勵卡或客服結果；每封信需能追溯來源事件與交易。Header／AppBottomNav 若顯示未讀 badge，需以信箱服務端未讀總數為準，不能只以當前分類列表計算。

目前沒有推播實作、未讀總數 composable、批次讀取、通知設定的服務端同步或 Web Push 權限流程；pushEnabled 僅為預留欄位，規格暫不宣稱已提供推播。

12. API、資料保存與目前缺口

目前信箱與設定都是 local／Mock 狀態：useMailboxState.ts 以 useState 種子信件，usePreferencesState.ts 只以瀏覽器 localStorage 保存部分偏好。API inventory 顯示尚未接實際 $fetch。

正式化需補信件列表／詳情／已讀／刪除／附件領取、未讀彙總、通知偏好、黑名單 CRUD、法律版本與登出 session API；並定義資料保留、裝置同步、撤銷、重試、稽核與個資刪除邊界。

Figma 需交付信箱桌面雙欄與手機列表／詳情 overlay、分類切換、未讀／已讀、附件可領／已領／失敗、空狀態與刪除提示；設定需交付四個區塊、開關、試聽、語言選擇、黑名單空／有資料、Legal Modal、登出確認與錯誤狀態。

12. 跨頁錯誤、回滾與一致性

  • 認證失敗：保留可安全恢復的目的地，清除無效 token，不能把受保護頁面當成已登入。
  • query 無效：以安全預設或清除 query，不能透過 URL 直接變更會員、遊戲、收件人或資產。
  • 領取／兌換失敗：不更新成功 UI；可重試時保留輸入，並使用冪等鍵避免重複發獎。
  • 贈禮建立／接受／拒絕／取消／逾期：保留案件狀態與保留資產的對應交易；退款不可只更新畫面。
  • 信箱附件：已讀與已領要分開；已讀不代表附件已入帳。
  • 登出：清除本次登入可見的受保護資料，但不應刪除正式帳戶服務上已完成的交易或案件。
