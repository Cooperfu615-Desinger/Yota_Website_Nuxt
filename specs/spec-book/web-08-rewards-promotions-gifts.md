## 1. 這個功能是什麼

本功能讓登入後玩家查看可用獎勵卡、預覽並兌換優惠碼，以及從保險箱或玩家小卡提出玩家對玩家贈禮申請。玩家應能在確認前看懂獎勵、費用、限制與結果，並在完成後由錢包、獎勵卡、交易紀錄或信箱讀回可追溯結果。

目前 Web 財務基準為 `NT$1 = 金幣 1 = 銀幣 100`；銅幣僅供試玩，不具儲值價值。獎勵卡、優惠碼與贈禮目前仍由 `useState`／local state 模擬，不能將畫面成功提示視為正式資產已入帳。

## 3. 名詞說明

| 名詞 | 定義 |
|---|---|
| 獎勵卡 | 帶有餘額、流水目標、轉換上限與期限的活動資產容器 |
| 活動銀幣 | 目前原型獎勵卡使用的活動單位；正式幣別與價值需由單一規則封存 |
| 優惠碼 | 玩家輸入後先預覽、再確認兌換的一次性活動識別碼 |
| 贈禮申請 | 玩家對指定收件人提出的金幣／銀幣轉移案件，需接受、拒絕、取消或逾期處理 |
| 手續費快照 | 建立贈禮申請時固定的 VIP 費率與計算結果，不能只採用頁面當下顯示值 |
| 收件人 | 由 `receiverId` 對應的其他玩家；query 只是導流意圖，不能作為授權依據 |

## 5. 欄位說明

| 欄位 | 顯示／輸入內容 | 限制與目前狀態 |
|---|---|---|
| card ID／來源 | 獎勵卡識別、活動來源、合併來源 | 目前由 `useRewardCardState.ts` 提供；正式需服務端識別 |
| balance／target | 卡片餘額、有效流水目標 | 需顯示幣別與進度；不可由前端自行認定可轉換 |
| conversion limit | 本次最多可轉換額度 | 目前以 `min(currentBalance, conversionLimit)` 候選；正式規則待確認 |
| expiresAt | 到期時間 | 顯示時區與不可操作原因；最後 72 小時合併限制目前為候選規則 |
| promo code | 最多 8 碼的大寫英數字串 | 前端可正規化與預覽；一次性消費由服務端負責 |
| reward preview | 活動名稱、類型、數量、期限、是否已兌換 | 預覽不等於已入帳，確認前不可變更資產 |
| receiverId／receiver | 收件人識別與可見名稱 | 必須由服務端重新驗證存在、權限、黑名單與登入狀態 |
| currency／amount | 金幣／銀幣與正整數金額 | 需檢查餘額、最小單位、每日上限與重複送出 |
| fee／receivedAmount | VIP 費率、手續費、收件人實收額 | 建立申請時保存快照；不可只信任前端計算 |

## 6. 狀態說明

### 6.1 獎勵卡狀態

卡片狀態為 `inactive | active | paused | converted | merged`。目前資料包含卡片 ID、來源、面額／餘額、流水目標、轉換上限、到期日、狀態與合併來源；卡片以 `useState` 保持跨元件狀態，但尚未接玩家帳戶服務端。

### 6.2 優惠碼狀態

優惠碼流程分為 `idle`、`previewing`、`confirming`、`success`、`invalid`、`expired`、`claimed` 與 `failed` 候選狀態。`usePromoCodeState.ts` 以會員識別維持已兌換紀錄與活動金幣餘額，預覽與兌換必須是兩個可辨識步驟。

### 6.3 贈禮申請狀態

`GiftRequest` 至少包含申請人、收件人、幣別、申請金額、手續費、實收金額、狀態、建立／到期時間與處理方向。案件狀態需表達 `pending`、`accepted`、`rejected`、`cancelled`、`expired`；目前狀態與餘額皆為前端 Mock。

## 7. 查詢、排序與分頁

- 獎勵卡列表至少要能依狀態、到期時間與可操作性排序；目前以 state 陣列顯示，未接正式查詢或分頁。
- 優惠碼需可查詢兌換結果與失敗原因；目前只保留前端會員範圍內的 mock claims。
- 贈禮案件需能依狀態、建立時間、處理方向與收件人查詢；正式 API 應定義 cursor、排序、時區與保存期限。
- 任何列表的空資料、查詢中、查詢失敗與重試入口，都不可被成功空畫面取代。

## 8. 操作與跳轉

### 8.1 獎勵卡啟用、合併與轉換

1. 玩家進入會員中心的獎勵卡分頁，查看可見卡片與限制。
2. 玩家可啟用符合資格的卡片；已啟用卡片依正式規則累積活動餘額。
3. 符合條件時可選取至少兩張卡合併；來源卡標為 `merged`，新卡為 `inactive`。
4. 完成流水後進行轉換，候選計算為 `min(currentBalance, conversionLimit)`；剩餘額度依正式規則處理。

### 8.2 優惠碼預覽與兌換

1. 未登入玩家點擊兌換區時開啟登入／註冊，並保留原目的地。
2. 已登入玩家輸入最多 8 碼的大寫英數字串，前端先正規化並顯示預覽。
3. 預覽顯示活動名稱、獎勵類型、數量、有效期限與是否已兌換。
4. 玩家確認後才執行兌換；成功後更新對應活動餘額、錢包或獎勵卡。
5. 格式錯誤、無效、過期、已使用、不可兌換與服務失敗均需可辨識，且重複點擊不可重複發獎。

### 8.3 玩家贈禮申請

1. 玩家從保險箱轉帳分頁或聊天玩家小卡選取收件人。
2. 輸入幣別與金額；前端先驗證收件人、正數、可用餘額與每日上限。
3. 預覽顯示原額、手續費、收件人實收額與 VIP 費率快照。
4. 確認後保留送禮者資產並建立待處理申請。
5. 收件人接受、拒絕，或送禮者取消；逾期案件進入 `expired`，並依正式規則退回保留額。

目前原型候選限制為單一玩家每日最多 10 筆、單筆上限 1,000,000、申請有效期 168 小時；未經後端契約與營運設定確認，不得視為正式規則。

## 9. 頁面狀態

需覆蓋未登入、載入中、空資料、預覽中、確認中、成功、格式錯誤、無效、已兌換、過期、餘額不足、收件人不存在、自己送自己、達到上限、權限不足、被封鎖、處理失敗、可重試、已取消、已拒絕與已逾期。任一錢包更新失敗時，兌換／贈禮應回滾或進入可查詢的待處理狀態，不可只更新畫面。

Guest 不得兌換優惠碼，也不應在未識別會員的情況下建立可領取贈禮；不可操作卡片需保留原因說明。最後 72 小時不可合併的規則若保留，必須在卡片、確認頁與 API 驗收中一致呈現。

## 14. 這個功能需要的資料

- 獎勵卡 ID、來源、幣別、面額／餘額、流水目標、轉換上限、到期日、狀態與合併來源。
- 優惠碼、會員識別、預覽結果、兌換狀態、獎勵類型、數量、期限與交易 reference。
- `GiftRequest` 的申請人、收件人、幣別、申請金額、手續費、實收金額、狀態、建立／到期時間與處理方向。
- 錢包快照、VIP 費率、idempotency key、交易 ID、前後餘額、失敗原因、退款／回滾與客服稽核資訊。
- `receiverId`、來源路徑、返回路徑與跨頁流程所需的 `WEB-FLOW-04`／`WEB-FLOW-05` 交接資料。

目前 `useRewardCardState.ts`、`usePromoCodeState.ts`、`useGiftState.ts` 與 `useFinancialState.ts` 只代表 Web 原型來源；正式接入前不得當成跨裝置持久資料。
