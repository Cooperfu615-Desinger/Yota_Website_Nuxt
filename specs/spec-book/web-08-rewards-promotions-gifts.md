# WEB SPEC 08｜獎勵卡、優惠碼與玩家贈禮

> 文件狀態：Phase 2 初版，已依目前 Nuxt 原型整理；正式 API、營運規則與最終視覺仍待確認。
> 工作單映射：`YOTAPLATFO-454`（SPEC）／`YOTAPLATFO-467`（Figma）／`YOTAPLATFO-480`（WEB／Nuxt）
> APP 參考：APP 07「獎勵卡」、APP 08「優惠碼」、APP 09「贈禮」；APP 文件只作為結構與產品語意參考，不直接覆蓋 Web 現況。

## 0. 文件狀態與範圍

本分冊統一描述 Web 登入後的獎勵與玩家對玩家資產互動：獎勵卡、優惠碼兌換、保險箱贈禮申請，以及從玩家小卡進入贈禮／轉帳的導流。公共活動頁只保留入口與文案關聯，詳細頁面規格放在 `web-02-public-site.md` 與 `web-09-tasks-events-rankings-tutorial.md`。

目前是前端 Mock 規格，不宣稱已具備可上線的錢包、反作弊、訂單、風控或後端兌換能力。

## 1. 產品目標與使用情境

| 目標 | Web 行為 | 正式化待辦 |
|---|---|---|
| 讓玩家查看可用獎勵 | 會員中心獎勵卡分頁顯示活動銀幣卡、狀態、餘額與門檻 | 由服務端提供玩家可見範圍與即時狀態 |
| 讓玩家兌換活動碼 | 輸入碼後先預覽，再確認領取 | 兌換鎖、風控、重複提交與稽核 |
| 讓玩家向其他玩家贈禮 | 從保險箱提出金幣／銀幣贈禮申請 | 收款人解析、費率快照、通知與交易一致性 |

使用者故事：`WEB-US-U-08-01` 玩家能找到自己的獎勵；`WEB-US-U-08-02` 玩家能在確認前看懂優惠碼結果；`WEB-US-U-08-03` 玩家能對指定玩家提出贈禮並知道處理狀態。

## 2. 名詞、貨幣與來源優先序

- `gold`：金幣；`silver`：銀幣；`bronze`：銅幣；`activity-silver`：獎勵卡使用的活動銀幣單位。
- 目前 Web 財務基準為 `NT$1 = 金幣 1 = 銀幣 100`；銅幣僅供試玩，不具儲值價值。
- 錢包與轉帳狀態以 `useFinancialState.ts`、`useGiftState.ts` 為目前原型來源；獎勵卡以 `useRewardCardState.ts` 與 `utils/rewardCardMerge.ts` 為目前原型來源。
- 若 APP、舊 handoff、營運文案與現行程式不一致，需在規格中標註差異，不以默認值覆蓋現行 Web 行為。

## 4. 介面與資訊架構

獎勵卡區需能區分「可啟用」「已暫停」「已轉換」「已合併」等狀態，並提供餘額、流水門檻、轉換上限、到期時間與可用操作。優惠碼區需依序呈現輸入、預覽、確認、成功／失敗訊息。贈禮區需區分可輸入對象、金額、預覽手續費、送出後的待處理案件與處理結果。

`RewardCardContent.vue`、`PromoCodePanel.vue`、`GiftRequestList.vue` 與 `VaultContent.vue` 是目前視覺與互動基準；正式 Figma 需補上空狀態、錯誤、過期、不可操作與手機版布局。

## 5. 狀態與資料模型

### 5.1 獎勵卡

卡片狀態為 `inactive | active | paused | converted | merged`。目前資料包含卡片 ID、來源、面額／餘額、流水目標、轉換上限、到期日、狀態與合併來源。卡片以 `useState` 保持跨元件狀態，但目前未接玩家帳戶服務端。

### 5.2 優惠碼

`usePromoCodeState.ts` 以會員識別（目前由 auth provider／account 組合）維持已兌換紀錄與活動金幣餘額。預覽與兌換分為兩步；成功後可能產生錢包獎勵、活動金幣或獎勵卡。

### 5.3 贈禮申請

`GiftRequest` 至少包含申請人、收件人、幣別、申請金額、手續費、實收金額、狀態、建立／到期時間與處理方向。案件狀態需可表達 `pending`、`accepted`、`rejected`、`cancelled`、`expired`；目前狀態與餘額皆為前端 Mock。

## 6. 主要流程：獎勵卡啟用、合併與轉換

1. 玩家進入會員中心的獎勵卡分頁。
2. 系統列出目前可見卡片與每張卡的狀態、餘額、門檻及期限。
3. 玩家可啟用卡片；已啟用卡片依遊戲／財務規則累積活動餘額。
4. 符合條件時可選取至少兩張卡進行合併；合併後來源卡標為 `merged`，新卡為 `inactive`。
5. 玩家完成流水後進行轉換，系統以 `min(currentBalance, conversionLimit)` 計算可轉換額度，剩餘額度依規則回收。

## 7. 主要流程：優惠碼預覽與兌換

1. 未登入玩家點擊兌換區，應開啟登入／註冊並保留原目的地。
2. 已登入玩家輸入最多 8 碼的大寫英數字串；前端先正規化並顯示預覽。
3. 預覽需指出活動名稱、獎勵類型、數量、有效期限與是否已兌換。
4. 玩家確認後才呼叫兌換動作；成功後更新對應活動餘額、錢包或獎勵卡。
5. 成功、格式錯誤、無效、過期、已使用、不可兌換與處理失敗均需可辨識，且不能因重複點擊重複發獎。

## 8. 主要流程：玩家贈禮申請

1. 玩家從保險箱轉帳分頁或聊天玩家小卡選取收件人。
2. 輸入贈禮幣別與金額；前端先驗證收件人、金額正數、可用餘額與每日上限。
3. 預覽頁顯示原額、手續費、收件人實收額與目前 VIP 費率快照。
4. 確認後從送禮者保險箱保留資產，建立待處理申請。
5. 收件人接受、拒絕，或送禮者取消；逾期案件進入 `expired`，應依規則退回保留額。

目前原型：單一玩家每日最多 10 筆、單筆上限 1,000,000，申請有效期 168 小時；這些值需在後端契約與營運設定確認後才可視為正式規則。

## 9. 例外、錯誤與不可操作狀態

- 優惠碼為空、長度超過 8、包含非英數字、無效、已使用或已過期時，不進入確認狀態。
- Guest 不得兌換優惠碼，也不應在未識別會員的情況下建立可領取贈禮。
- 餘額不足、金額低於最小單位、收件人不存在、自己送給自己、達到每日上限時，送出按鈕應阻擋並提供原因。
- 到期前最後 72 小時的獎勵卡不可合併但仍可啟用；不可操作卡片需保留原因說明。
- 任一錢包更新失敗時，兌換／贈禮應回滾或進入可查詢的待處理狀態，不可只更新畫面。

## 10. 合併、費率與資產一致性規則

目前 Web 合併規則為至少兩張、無固定張數上限，僅允許 `inactive` 或距離到期超過 72 小時的 `paused` 卡片；新卡取最早到期日，餘額、流水門檻與轉換上限依目前工具相加，來源卡標記為 `merged`，新卡仍可再合併。

贈禮手續費依送禮者 VIP 等級計算，預覽需固定本次費率快照；服務端應以交易建立時的快照為準。所有資產變更都需要交易 ID、來源、時間與可追溯的前後餘額。

## 11. 權限、安全與風控邊界

- 只有已驗證登入會員能兌換優惠碼、啟用／轉換獎勵與建立贈禮。
- 會員只能讀取自己的卡片、兌換紀錄、錢包與贈禮案件；只能在授權狀態下讀取收件人公開識別。
- 優惠碼兌換必須由服務端做原子性的一次性消費，前端 `claimsByMember` 僅是 Mock。
- 贈禮需有防刷、速率限制、黑名單／停權檢查、重複請求去重與客服稽核能力。
- 金額不可由前端決定；前端顯示的 VIP 費率、餘額與到期日都不是授權依據。

## 12. API、事件與目前缺口

目前 `2026-07-29-api-inventory.md` 顯示前端沒有實際 `$fetch` 交易呼叫，相關功能仍以 composable 與 local state 模擬。正式化至少需要：優惠碼預覽／兌換、獎勵卡清單／狀態／合併／轉換、贈禮建立／查詢／接受／拒絕／取消／到期，以及錢包與交易紀錄事件。

需要補定的事件：`reward.claimed`、`reward-card.activated`、`reward-card.merged`、`reward-card.converted`、`gift-request.created`、`gift-request.resolved`。所有事件需可與信箱、通知、客服查詢與財務對帳關聯。

## 13. Figma 交付內容

Figma 需交付桌面與手機版：獎勵卡清單、卡片詳情／啟用、合併選擇、轉換確認、優惠碼輸入／預覽／成功／錯誤、贈禮輸入／預覽／待處理清單／案件詳情，以及登入、餘額不足、空狀態、過期和權限不足等狀態。

每個操作需標示幣別、數字格式、不可操作原因、確認前後差異與返回路徑。動線需能從玩家小卡進入轉帳後回到原聊天脈絡，並覆蓋深連結 `receiverId`。

## 14. Nuxt 實作邊界

現行元件與 composable 應維持單一狀態來源：`RewardCardContent.vue`／`useRewardCardState.ts`、`PromoCodePanel.vue`／`usePromoCodeState.ts`、`GiftRequestList.vue`／`useGiftState.ts`、`VaultContent.vue`／`useFinancialState.ts`。登入、頁面導流與 Modal 需遵守 `ClientOnly`／`Teleport` 的 SSG 規則。

正式 API 接入前不得把 local state 當成跨裝置持久資料；正式接入後需處理 hydration、重試、交易結果與離開頁面的未完成確認。瀏覽器階段測試碼只能存在於測試環境，不得成為正式兌換規則。
