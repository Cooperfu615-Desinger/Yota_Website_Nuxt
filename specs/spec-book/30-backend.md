## 3. 拍板後的第一階段範圍變化

依 [決策文件](../decisions/2026-07-30-first-phase-alignment-decisions.md)，`api-master-list.md` 原本標 ⏸ 的 21 支（A-5~A-7）中，有 7 支（A-7 贈禮全組）已解封可以直接開工；A-6 儲值組維持原設計不用重新討論方案；A-11 VIP 組的**資料結構**可以開工，但**門檻數值**（各級要儲值/投注多少）仍是 §6 決策 #11，需要業務先給數字。

**尚未解封、仍會卡住開發的 §6 決策**（`api-master-list.md` 原編號，未被本輪拍板涵蓋）：

| # | 決策點 | 為什麼還沒解 |
|---|---|---|
| 1 | 黑名單指哪一個（社交封鎖 vs IP封鎖） | 本輪未涉及，需另外找時間拍板 |
| 2 | 金額傳輸型別（string vs number） | 技術規範，非本輪的三方畫面落差範疇 |
| 5 | 獎勵卡流水認列規則 | 需要業務定義「什麼下注算流水」，本輪決策只確認了官網要補流水機制的必要性（見前端冊 §6），沒有定規則 |
| 6（範圍部分） | 遊戲 catalog 最終要幾類幾款 | 本輪決策明確表態「不現在決定」，留給營運/採購階段 |
| 7 | 好友是否雙向同意 | 未涉及 |
| 8 | 工單狀態揭露幾段 | 未涉及（本輪只核對修正了「同時進行中上限」為 1 筆，非狀態機段數） |
| 9 | 選座位是否納入 | 未涉及，官網 `SeatSelectionModal.vue` 仍是 dead code |
| 10 | 檢舉是否獨立於工單 | 未涉及 |

**建議**：#1、#2、#11 影響範圍最廣（#2 影響所有金流端點、#1 影響後端時程既定的「10. 黑名單」項目、#11 卡住 VIP 頁面能不能真的上線），適合作為下一輪拍板的候選。

## 4. 交付優先序建議

在 `api-master-list.md` 原本的 §7 建議推進順序基礎上，疊加本輪拍板結果：

1. **§6 決策 #1、#2**（黑名單定義、金額型別）—— 不決定，A-5~A-7 共 21 支端點仍無法真正定案 schema，即使 A-7 已解封「要做哪 7 支」，金額型別不定，每支的 request/response 都是暫定
2. **A-7 贈禮組**（7 支，已解封）—— 官網有完整測試覆蓋（`tests/giftRequest.test.mjs`、`tests/vaultTransfer.test.mjs`）可直接當業務規則契約，是本輪拍板後最適合優先開工的一組
3. **A-5 錢包二維重構** —— 其他金流模組（儲值/贈禮/兌換/獎勵卡）都依賴它，維持 `api-master-list.md` 原判斷不變
4. **A-11 VIP 資料結構**（欄位已定，數值待補）—— 先把 `promo_deposit`/`promo_turnover` 等欄位加上去，數值可先用預設值上線，數值本身走 §6 決策 #11 另外拍板，不阻擋開發
5. **A-8 獎勵卡流水認列**（§6 決策 #5）—— 後端排程已是 8/3，建議與 #11 一起排進下一輪拍板議程，避免卡開發時程
