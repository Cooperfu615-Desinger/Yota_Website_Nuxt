## 0. 文件狀態與範圍

本分冊涵蓋每日簽到／里程碑、活動列表與詳情、排行榜，以及新手教學／APP 下載引導。公共入口在 `web-02-public-site.md` 有摘要，本文件補充登入後 `/lobby/*` 的頁面布局、導流與狀態。

目前資料集中於 `siteContent.ts`，簽到互動由 `pages/lobby/daily.vue` 與相關 composable 模擬，不代表正式活動服務已完成。

## 1. 產品目標與使用情境

- 玩家可快速知道今天是否完成任務、錯過哪幾天、可否補簽與下一個里程碑。
- 玩家可依活動狀態與類型找到活動，讀取獎勵與截止時間，再導向儲值、遊戲或登入流程。
- 玩家可查看不同榜單與個人排名脈絡，理解榜單用途、更新狀態與活動期間。
- 新玩家能在 Web 中取得遊戲、平台與加入主畫面的基本教學，並知道 Web 與 APP 的功能邊界。

## 2. 入口、路由與頁面對照

| 功能 | 公開頁 | 登入後大廳頁 | 主要來源 |
|---|---|---|---|
| 每日簽到 | 活動入口／活動詳情 | `/lobby/daily` | `pages/lobby/daily.vue` |
| 活動 | `/events` | `/lobby/events` | `siteContent.events`、活動頁元件 |
| 排行榜 | `/leaderboard` | `/lobby/leaderboard` | `siteContent.leaderboard` |
| 教學 | `/tutorial` | `/lobby/tutorial` | `siteContent.shortcutGuides`、教學頁元件 |

未登入進入受保護的每日簽到或大廳活動頁時，應依 Web 導覽規則開啟登入並保留原目的地；公共活動／排行榜／教學可先讀取公開內容。

## 3. 每日簽到的介面結構

每日任務頁以 31 天日曆／進度視覺為核心，需呈現當日日期、連續進度、每日獎勵、里程碑標記、今日操作與補簽入口。已完成、今日可簽、今日待處理、漏簽、未開始等狀態要有不同視覺與可操作性。

里程碑卡需連結獎勵卡規格；活動金幣、活動銀幣與獎勵卡不能只以相同色彩區分，必須顯示完整幣別與領取結果。

## 4. 每日任務資料與狀態

目前每日獎勵由 `siteContent.dailyCheckin.dailyRewards` 提供，共 31 天；里程碑為第 5、7、10、15、20、25、30 天；補簽成本為每日 100。頁面目前以 `useState` 保存已簽天數與已領里程碑，重新整理／換裝置不代表正式持久化。

狀態模型至少包含：日期序號、日曆日期、是否已簽、是否為今天、是否可補簽、是否已領里程碑、獎勵內容與處理狀態。正式服務需另提供伺服器時間、連續簽到計算與不可竄改的領取紀錄。

## 5. 每日簽到主要流程

1. 玩家進入 `/lobby/daily`，系統取得伺服器時間與本期簽到資料。
2. 玩家點擊今日簽到；未登入時先要求登入。
3. 成功後更新今日狀態、金幣／獎勵卡餘額與里程碑進度。
4. 若有可領里程碑，玩家可逐項領取並看到成功提示；不可重複領取。
5. 玩家可查看漏簽日，選取符合條件的日期進行補簽；補簽前需顯示成本與確認。

## 6. 補簽、里程碑與差異標記

補簽必須驗證玩家餘額、可補日期、活動期間、每日／整期限制與重複請求。扣除成本與補發獎勵需是同一筆可追蹤交易。

目前 `siteContent.ts` 的第 10／15／20 天標示為活動銀幣獎勵，而 `useRewardCardState.ts` 另以活動銀幣獎勵卡定義；舊的前端敘述曾出現不同幣別說法。Web 規格暫以現行程式來源標為「待正式規則封存」，不可在 Figma 或 API 任一側自行定案。

## 7. 活動列表與活動詳情

活動列表需提供進行中、即將開始、已結束等狀態分組或篩選，活動卡顯示主視覺、標題、副標、獎勵、截止時間與是否為儲值相關活動。活動詳情需列出資格、玩法、期間、獎勵發放、導流按鈕與注意事項。

目前 `siteContent.events` 是靜態資料，含 `active`、`upcoming`、`ended` 與 `deposit` 標記；未來需由 CMS／活動服務提供時間與資格，不應以瀏覽器時鐘單獨判定活動狀態。

## 8. 排行榜資訊架構

排行榜提供「倍數榜」「贏分榜」「富豪榜」三個 Tab。每個榜單至少有前三名視覺、後續列表、玩家名稱／識別、成績、遊戲或來源與更新／活動期間說明。若登入，應提供「我的排名」或清楚說明目前未提供該功能。

目前 `siteContent.leaderboard` 提供 preview、top3 與 rest 靜態資料；Web 版需明確標示這是原型資料，不能讓玩家誤認為即時獎金或結算結果。

## 9. 排行榜流程與例外

玩家可切換榜單、查看排名內容、由活動卡導向榜單。載入中、暫無資料、活動未開始、活動已結束、服務錯誤與玩家未上榜需各有狀態。榜單數字需固定千分位、正負號與幣別／倍率格式。

若服務端回傳排名版本或更新時間，頁面需顯示時間；若跨頁切換，不應沿用另一榜單的 Tab 狀態或舊資料。

## 10. 教學與加入主畫面流程

教學頁提供平台介紹、遊戲使用方式、Web／APP 差異與 iOS／Android 加入主畫面的步驟。`siteContent.shortcutGuides` 目前包含 iOS 與 Android 的瀏覽器、說明與步驟；安裝／信任企業開發者等文案需標示作業系統版本差異。

教學導流按鈕應能回到首頁、登入或遊戲大廳；若是外部下載連結，需在正式規格補上版本、檔案完整性、風險提示與失效 fallback。

## 11. 權限、時間與資料邊界

- 公開活動、排行榜與教學可以讀取公開內容；每日簽到、個人任務與領取操作必須登入。
- 簽到／活動資格／榜單結算均以伺服器時間與伺服器資格為準，瀏覽器時間只作顯示輔助。
- 玩家不得從 URL query 或前端 state 自行改寫日期、獎勵、榜單分數或領取狀態。
- 活動獎勵發放要與錢包、獎勵卡、信箱和交易紀錄具備可追溯關聯。

## 12. API 與目前缺口

目前未見實際 `$fetch` 活動／任務／榜單呼叫；API inventory 與 gap analysis 已列出活動資格、排行榜即時資料、簽到持久化與獎勵發放等候補缺口。正式化需補：活動列表／詳情、任務進度、簽到、補簽、里程碑領取、榜單查詢、我的排名、活動版本與伺服器時間。

需要定義重複請求與離線重試、活動切換時的資料快取、排行榜分頁／游標、獎勵發放失敗補償與客服查詢依據。

## 13. Figma 交付內容

Figma 需交付四個功能頁的桌面／手機布局，以及所有主要狀態：載入、空資料、未登入、已簽／可簽／漏簽／補簽確認、里程碑可領／已領、活動分組、活動詳情、榜單 Tab、未上榜、活動結束與教學步驟。

每日頁需特別標示幣別與獎勵卡入口；活動／榜單卡片需可追溯至公共頁與大廳頁的共用元件，避免兩套視覺規則分裂。

## 14. Nuxt 實作邊界

頁面使用 `layout: 'lobby'` 的大廳框架；公開頁沿用 default layout。每日簽到狀態目前在頁面與 composable 間以 `useState` 傳遞，正式接 API 後不得以 local state 作為最終權威。公共與大廳相同內容應由資料層重用，不應複製兩套硬編碼文案。

倒數與活動狀態需避免 SSG hydration 差異；所有會讀取瀏覽器時間、localStorage 或產生互動 Modal 的邏輯應在 client 端安全初始化。
